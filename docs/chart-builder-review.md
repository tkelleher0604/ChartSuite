# Building a chart through the GUI

This branch makes graphics reusable projections of records. Paragraphs mix ordinary text with editable record fields; an explicit scope governs both data and presentation edits. Blank charts offer direct object creation and drawing-to-type conversion. Start with the [scoped editing contract](scoped-canvas-model.md), then use the workflows and review boundaries below. The earlier [text review](editor-text-review.md) and initial GUI exercises remain historical evidence.

## What a user can do

1. Use the visible **New chart** action. A fresh profile opens the chart chooser before the example. Begin blank or use a template. **Add object** is on the page and in the toolbar; when the chart has one type, it names that type, such as **Add person**. Enter a name and either choose an existing object type or type a new one.
2. Choose **Design a reusable card** on the blank page or in Insert to begin with a name field, or draw and group shapes freely. Their text panel accepts ordinary text and offers **Merge field → New field…**. Literal braces remain literal; field chips bind to record values.
3. Select the grouping and choose **Save as object type…** in the side panel. Name the type and optionally its first object, then review fields and datatypes. This dialog omits the separate design-name and scope controls. Saving creates the schema, standard design in this view, and first object. One Undo restores the drawing and removes those additions.
4. Add another object of that type. It inherits the design with independent data. Ordinary formatting starts at **This box**; shared changes require choosing an **All** scope. The data panel has **Edit shared design**, which follows the existing design's scope instead of expanding a category design to the entire root kind.
5. Double-click a record's paragraph to edit its resolved text directly on the canvas: for example, `Please contact Maya about the launch.` Entering a field highlights its value and corresponding panel entry. Typing there changes the record; typing outside it changes the constant paragraph. **Apply edits to** governs both kinds of edit. **Merge field → New field** asks for a name and datatype, then saves the schema and paragraph insertion together. Invalid dates or numbers retain the draft with an explanation. In the structural design editor, field-name chips expose the template itself. Literal braces stay literal, and selected text can have its own formatting.
6. In the design editor, a persistent searchable **Fields** panel shows sample values. Click to insert at the text caret or drag into the active paragraph. Existing words, including an uncommitted text draft, stay in place. **New field** stages a typed definition, including numbers, choices and yes/no fields. **Done** saves definitions and design in one change; **Discard** saves neither.
7. Choose **Stack text** for a card that moves following text out of the way as values grow, or **Free position** to keep independently placed layers where they were drawn. Each text frame has **Grow height**, **Fixed frame**, and **Shrink to fit** sizing. Arbitrary multi-layer drawings retain their positions, widths and alignment when converted to a type.
8. An individual or narrower-group design edit forks its resolved design; an edit at its existing shared scope updates its linked uses. **Use shared design** removes only the selected object's Design note, preserves its data and other formatting, and supports one-step Undo.
9. Select ordinary text in a live paragraph and drag it into the record panel, or use **Make selected text a field**. The prompt asks for the schema name. Accepting creates the entry and replaces exactly that occurrence with a binding; Cancel changes nothing. A broader scope shows the affected count and offers the current object alone. Conflicting existing values block the operation.

The first instance uses the supplied object name, falling back to the type's name. Designs remain scoped to views. Linked fields such as “Owner's name” retain their meaning; saving a new type does not invent relationships. A single unambiguous full-card backing becomes the design's background, so it grows with content without a duplicate painted frame. Decorative shapes retain their geometry. No schema or log migration is required.

## Review boundaries

- `app/ui/canvas.js`: object creation reuses the existing placement and transaction path; literal shape editing uses TextTemplate; field drops prefer visible design parts over an overlapping “Other fields” frame.
- `app/core/design-schema.js`: pure planning for affected types, field inference and validated declarations. A shared design reaches every note that uses it, including other views and types with no visible instance. Field types are inferred from the full source path and type; unrelated choice options are never pooled. Declaration conflicts return no partial plan.
- `app/core/design-geometry.js`: pure conversion between one record's expanded preview and authored design coordinates. It preserves manual moves, sizes and connector points, restores unchanged format references, and keeps temporary editor metadata out of saved parts. The design session supplies measurement and persistence.
- `app/ui/designs.js`: commits schema declarations and the design together. Only fields explicitly created during an existing design edit are declared on Done. Existing relative tokens must never become own fields merely because the design was edited. Validation happens before closing the editable draft.
- `app/ui/words.js`: shared literal text, field chips, caret handling and rich-text edits. Adapters provide fields and persistence; the control does not look up records or write transactions.
- `app/core/edit-scope.js` and `bound-text.js`: full-state scope resolution, source/display span projection, exact record targets and validated bulk value plans. `Scene.recordDesign` shares the renderer's design precedence for off-page records.
- `app/ui/bound-words.js` and `canvas-bindings.js`: editable resolved values, draft validation and record-panel synchronization. The adapter sends accepted values through `App.putBatch`, retaining dates, fixed facts, reviewed changes and one-step Undo.
- `app/ui/field-extraction.js`: validates the selected occurrence, proposes schema declarations and prompts for the name. Its adapter commits data, schema and template together.
- `app/ui/canvas-words.js`: the in-place editor's focus and overlay lifecycle. Only one editor owns a layer's draft; switching between canvas and panel commits it before the other editor opens. Selected-text formatting uses the same source coordinates as field substitution.
- `app/ui/field-palette.js`: reusable field search, samples and insertion/drag controls; adapters own discovery and writes.
- `app/core/formatting.js`: formatting command planning and transaction application extracted from the toolbar. Footer properties read transaction-current state so one multi-property change cannot overwrite its earlier properties.
- `app/core/tree.js`: cycle-safe owned-entry traversal shared by formatting, Scene and the inspector. Active choice branches expose their conditional fields and relationships consistently.
- `app/ui/inspector.js`: ordinary shapes and design parts use the same text controls. The standalone inspector still supports running without the design/canvas modules.
- `app/ui/shell.js`, `formatbar.js`, and `canvas.css`: one empty-canvas prompt, visible creation actions, and toolbar sizing.

The workbook continues to store records, schema specs, and scoped Design notes. There is no second object store or separate canvas document to reconcile. The [formal editing contract](scoped-canvas-model.md) separates selection, scope and operation, and identifies which state each action changes. Tests of the existing source syntax, formulas, scope, undo, and exports remain in their existing suites.

The display contract separates a text block's content, its fit behavior, the card's layout, and the record supplying its values. `Design.layout` and `format.Fit` are optional; absent values retain legacy behavior. A free-position card can grow around a growing text frame without moving its neighbors. Fixed frames report overflow; only explicit shrink-to-fit reduces text size. The editor distinguishes automatic preview growth from authored moves and resizes, so editing a long record does not save that record's expanded dimensions as every object's minimum size.

The design sandbox also guards chart creation, duplication, deletion, renaming, workbook opening and presentation export until Done or Discard. Those actions cannot accidentally operate on the temporary editing workbook. Workbook file saving continues to use the committed storage session.

## Acceptance checks

Open [builder-test.html](../app/tests/builder-test.html) in Chrome or Edge. It starts with an in-memory sample workbook, then creates blank charts through the gallery. All authoring goes through controls, contenteditable text, keyboard shortcuts, and pointer events. Model APIs are read only in the acceptance script. The fixture replaces workbook storage and native file picking; save/reopen round-trips a serialized workbook. Preferences are isolated in memory too.

The builder test creates objects and a grouped drawing, creates a type and its schema, checks literal text beside fields, verifies Cancel and reserved names, exercises Undo/Redo, fills individual records, drags a field into a part, saves and discards design edits, draws a relationship, and saves/reopens the result. It also checks that a later object inherits the design.

The separate [design-editor flow](../app/tests/builder-test.html?flow=design-editor) covers the persistent palette, saved caret and pending text during insertion/dragging, Add text followed by sidebar typing, typed schema creation, shared category designs, individual forks, returning to a shared design, duplicate views, Undo/Redo, and exported text staying inside a growing background. The [classification flow](../app/tests/builder-test.html?flow=classification) authors conditional fields and verifies that independently applied built-in designs do not accidentally share subsequent edits. The pure classification checks cover qualified paths for nested fields with the same name and legacy unqualified tokens.

The [canvas paragraph flow](../app/tests/builder-test.html?flow=canvas-text) builds a mixed paragraph and reusable type, then edits resolved values directly. It checks draft mirroring, invalid dates, blank values, panel edits, whole-type edits, a two-object selection excluding a third, reflow without losing the caret, Undo and serialized save/reopen. The [field extraction flow](../app/tests/builder-test.html?flow=field-extraction) selects a repeated literal, drags it to the panel, names the field, checks cancellation and conflicts, and undoes schema/data/template together. These flows never write product state through model APIs.

The [pending-edit flow](../app/tests/builder-test.html?flow=pending-bindings) seeds historical records, then uses the canvas, scope controls and confirmation bar to exercise dated changes. It closes and reopens shared/individual paragraph drafts, reopens an extracted field before confirmation, cancels proposals, and checks one-step Undo after confirmation. The simple-field cases also cover ordinary chart fields and single-token design layers; an untouched editor never applies a broad write, while deliberately retyping the current value does.

The [live field-creation flow](../app/tests/builder-test.html?flow=live-field-create) creates a blank chart and reusable type through the GUI, then inserts typed fields into an ordinary record paragraph. It checks cancellation, schema conflicts, one-object and broader insertion, editing blank fields, panel synchronization, and atomic schema/template Undo. Clean captures show the [narrow live editor](review-evidence/live-fields-narrow.png), [dark live editor](review-evidence/live-fields-dark.png), and [field palette](review-evidence/fields-palette.png).

For visual review, the builder supports `?stop=blank`, `?stop=save`, `?stop=cards`, and `?stop=finished`. The design flow supports `&stop=palette`; the paragraph flow supports `&stop=paragraph` and `&stop=live`. These stop at the relevant UI and hide the test report after successful checks. These are scripted DOM-event browser tests, not trusted hardware-input automation or a human usability study. The PowerPoint ease-of-use goal still needs a short human task comparison.

Current verification consolidates **4,051 passing checks across all 31 registered suites**, with no remaining failed or incomplete suite. Both the 1024×900 light and 1440×1000 dark presentations pass the full design, live-text and extraction flows. The canvas suite's 791 checks combine passing main/templates/craft results with the final 332-check formatting rerun; unchanged core results are retained. The [verification record](review-evidence/verification.json) identifies revision `1a61211`, each evidence set, component counts, additional visual captures and source hashes. It also records superseded failures and their resolutions. The earlier 3,561-check result at `508c44a` predates this redesign.

The storage tests include a delayed two-tab rename and an atomic creation failure. The text/editor tests cover native contenteditable deletion, Undo/Redo, formatting after blur and subsequent edits. The runner captures only completed reports, retains failures and incomplete runs honestly, and saves DOM, screenshots and browser logs alongside counts.

## Human review handoff

Run the command in [README](../README.md), then try the blank-page card task with actual mouse and keyboard input. The runner includes the separately selected canvas-entry checks and both formula-editor modes; the main canvas suite includes its formatting, template and craft sub-suites. Inspect the final screenshots as well as the result counts.

For a short human walkthrough:

1. Start blank, choose **Design a reusable card**, and make `Contact {Name} about {Project}.` with the field picker. Save it as a new object type.
2. Add two objects and give them different Project values. Double-click one paragraph and edit its Project value; check the panel and the other object.
3. Choose **All**, change the constant wording, and verify both objects. Set a shared Project value, then Undo and verify the original distinct values return.
4. Edit the shared design from the object with the longest text. Add a field, finish, and confirm shorter cards stay compact. Try free positioning and stacking.
5. Select literal words and make them a named field through the panel. Undo, save, reopen, and inspect the result. Record where a control needed explanation and compare task time with an equivalent PowerPoint chart.

Review the changes in this order: [scoped editing contract](scoped-canvas-model.md); `EditScope` and `BoundText`; temporal batch writes in `App.putBatch` and `Log.tx.at`; the shared text controls and canvas adapter; then layout/conversion and their GUI cases. No schema migration, second canvas document, new dependency or build step was introduced. The unfinished Claude branches listed in [editor-text-review.md](editor-text-review.md) remain a separate review queue.

Remaining usability questions for humans are the distinction between selecting a design part and its enclosing object, whether the shared edit scope and the displayed object's values are clear, and whether the complete task is faster than PowerPoint. The single card background grows automatically; arbitrary decorative graphics can still need manual arrangement. Returning to a shared design finds the matching kind/category rule. A finite selection saved as separate object patterns has no retained membership provenance after an individual fork, so the app does not guess how to rejoin that former set. Local GUI, persistence and exports were exercised; live Microsoft tenant integration is not established by the mocked remote-store tests.

## Kinds versus choice fields

Keep kinds for structural differences for this iteration. Use choices for classifications: for example, Person with Role and Department, or Entity with Legal form. Separate kinds for every department or visual appearance would duplicate schema without adding useful meaning.

Kinds currently anchor schema locations, relationship roles, formulas, tables, filters, and scoped notes. A choice is an entry on an object, while a kind identifies the object's root. Removing the root kind is consequently more than a rename of the type picker. A replacement must define which fields and relationship roles apply to an object, how that applicability changes when its choices change, and how existing historical logs retain their meaning.

The executable [classification comparison](../app/tests/classification-test.html) now models the same employment chart with distinct kinds and with one Object kind plus Category choices. It compares field applicability, constrained relationships, related merge text, designs and SVG output. The [GUI flow](../app/tests/builder-test.html?flow=classification) builds conditional fields through the controls and verifies independent values. This exposed and fixed missing blank fields under active choices and inconsistent relationship/field traversal. See [core contracts](../app/core/README.md#tree) for the model and limitations.

The experiment also shows why a migration is premature: changing a populated classification keeps its dependent data and infers broader schema. The UI can use pre-existing constrained relationships but cannot yet fully author endpoint classification constraints in the new-connection form. A replacement needs explicit reclassification semantics, historical compatibility and that authoring path. No duplicate type choice or migration is introduced here.

Schema planning, text editing, field picking, formatting writes, scope membership and bound-value planning now have separate modules. The design session lifecycle and the large canvas module still contain several responsibilities; this branch does not claim to finish the architectural cleanup.
